# 11 — Developer Experience: Makefile & CLI

> `Makefile` is the human entry point. `tsir` (`@tsir/console`) is the framework's operation surface. Both must work before any framework code exists — which is why they are written in Phase 0.

---

## 1. Makefile contract

The Makefile is a **thin dispatcher**: every target prints what it runs and delegates to `bun` or a tool script. No business logic in Make.

> **Naming convention:** the CLI namespaces commands with colons (`tsir migrate:status`), Make targets use hyphens (`make migrate-status`) because a colon in a Make target name is parsed as a prerequisite separator. The same operation must not have two spellings without a documented reason.
>
> **Scope (ADR-0031, `18-core-vs-distribution.md`):** the Makefile is the _framework's_ entry point. Application verbs — `migrate`, `db:seed`, `deploy:*`, `route:*`, `openapi:generate` — live behind `dist/tsir` and have no `make` spelling at all. Rows below that originally proposed one are struck through with the reason. `make make-check` (DXS-015) keeps this table honest against the file.
>
> **The test for "is this a `make` target?": does it describe an application, or the framework?**
> If the answer is an application — a project's routes, its deploy units, what an emulator can prove
> about the AWS calls _it_ makes — it is a `tsir` verb, and it has to work in a distribution where
> `src/tools/` does not exist. If it builds the framework (packaging, gates over `src/`, releasing),
> it is `make`. `deploy:verify` is the case that taught this: it was written as `make aws-emulator`
> because the check _reads_ framework source, and that reasoning was wrong — the question it answers
> belongs to the project in front of the developer, and the evidence it needs ships inside
> `@tsir/deploy`. A `make` gate that has to be taught about a package's fixtures is a sign the verb
> is in the wrong surface.

### 1.1 `make dev` semantics

```
make dev
  └── make kill-owned          (always; safe when nothing is running)
  └── bun src/tools/dev.ts     (starts services, prints URLs, supervisable)
```

- `make kill-owned` is **idempotent** and **scoped**: it reads `.tsir/dev.json`
  (written by `src/tools/dev.ts`) and signals only those PIDs, then verifies the
  recorded ports are actually free.
- It never uses `pkill -f node`, never kills by name, and never kills a PID it did
  not record. If a recorded PID is gone but the port is still bound, it reports
  the owning process and **does not** kill it. (Full algorithm in
  `src/tools/kill-dev.sh` header.)
- `make dev` re-runs this cleanup before binding, so a crashed previous run never
  blocks startup. It deliberately does **not** run the full sweep below: starting
  our dev server must not kill someone else's project.

### 1.1.1 `make kill` — the host port sweep

`make kill` is the command you run when a port is stuck and you do not care who
holds it:

```
make kill
  └── make kill-owned          scoped: our recorded processes
  └── make kill-ports          sweep: every listening TCP port, minus the protected set
```

The sweep (`src/tools/kill-ports.ts`) enumerates listeners with `ss -lntp`
(Linux) or `lsof -nP -iTCP -sTCP:LISTEN` (macOS), then applies a protection
policy _before_ signalling anything:

| Never touched                                           | Why                                                                                               |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Docker/containerd/Colima/Podman/OrbStack processes      | Losing the container runtime because you wanted port 3000 back is not an acceptable failure mode. |
| Docker ports `2375 2376 2377 7946 4789`                 | The daemon API, swarm and overlay ports belong to the runtime even if a user process holds them.  |
| System ports `22 53 123 631 5353`                       | sshd, DNS, mDNS and CUPS are not yours to restart.                                                |
| Data services `3306 5432 6379 9200 9300 27017 5672`     | Dropping a developer's database is not "cleanup". `--include-infra` opts in.                      |
| PID 1, this process, its parent, other users' processes | A dev tool that can signal root is a dev tool that can kill the machine.                          |
| Anything whose PID cannot be read                       | "Somebody else owns this" is a report, not a licence.                                             |

What remains — stray `bun`/`node`/`vite`/watcher processes — gets `SIGTERM`,
then `SIGKILL` after `--grace` (default 3000 ms), and every port is re-checked
afterwards. The command exits non-zero if a port survives, and prints one row per
port with the decision and the reason, so the table itself is the audit log.

```
  ✗  3000  bun                  killing — bun
  ·  5432  postgres             keep — data service (pass --include-infra to free)
  ·  2376  docker-proxy         keep — container runtime (docker-proxy)
```

`make kill-ports-dry` prints the table without signalling anything; `make kill
KILL_ARGS=--include-infra` widens the sweep to data services.

Rationale for the split: the phase-1 requirement is that a _stuck port_ can
always be recovered without hand-hunting PIDs, while `make dev` keeps the narrow
guarantee that it only touches what it started. Those are different jobs and they
now have different commands.

### 1.2 Graceful shutdown

`src/tools/dev.ts` installs `SIGINT`/`SIGTERM` handlers, stops accepting connections, drains in-flight requests (bounded 5 s), removes its PID/port record, and exits `0`. Ctrl-C therefore never leaves the port held.

---

### 1.2.1 Caches stay out of the workspace

Two directory classes are generated rather than authored, and both are gitignored:

| Path                                                                | Written by                                | Why it matters                                                                                      |
| ------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `.cache/bun`                                                        | package cache (`BUN_INSTALL_CACHE_DIR`)   | ~74 MB; Bun defaults to `$HOME/.bun`, which is _inside_ the project whenever the project is `$HOME` |
| `dist/`, `coverage/`, `.verify/`, `.tsir/`, `src/bench/latest.json` | build, coverage, verify-dist, dev runtime | regenerable, sometimes large                                                                        |

`make clean-cache` deletes all of them. The Makefile exports
`BUN_INSTALL_CACHE_DIR ?= $(CURDIR)/.cache/bun` so the package cache never lands
in the repository root in the first place — `[install] cacheDirectory` in
`bunfig.toml` is _not_ honoured by Bun 1.4.4 (verified via `bun pm cache`), so
the environment variable is the mechanism that actually works.

### 1.3 Flag parsing

Spec keys are written as they are typed (`'--json'`); `parseArgs` normalizes the
dashes once and every accessor (`boolFlag`, `stringFlag`) does the same. Until
this was fixed, every command declared flags that the parser could never match,
so _no_ flag worked — `tsir dev --json` silently ignored `--json` and every
command treated any flag as unknown. It survived because each command was tested
by hand only in its flagless form; `args.test.ts` now covers both spellings,
inline values, defaults and the three usage errors.

## 2. CLI surface (`@tsir/console`)

Two entry points over **one** command table: the global `tsir` (scaffolding, and anything run
before a project exists) and the project's own `ract` (§ 2.6). Groups are namespaced with `:`.

### 2.1 Lifecycle & quality

```bash
tsir dev [--host 127.0.0.1] [--port 3000]  # exported fetch handler; restart after edits
tsir build [--out .tsir]              # application manifest and drivers
tsir start                            # production boot with manifest
tsir test [Bun test flags]
tsir lint / tsir typecheck
tsir doctor [--fix]                   # env, tsir.js, deps, ports, manifests, versions
```

### 2.2 Generators

```bash
tsir new acme-api                     # scaffold an application (presets, .env.example, tsir.js)
tsir make:module shop
tsir make:controller order shop [--path /api/order] [--unit http]
tsir make:model order shop [--dialect sqlite|postgres]
tsir make:service UsersService
tsir make:migration create-orders shop
tsir make:seeder order shop
tsir make:middleware RequireTenant
tsir make:guard JwtAuth
tsir make:policy InvoicePolicy
tsir make:job SendInvoiceEmail
tsir make:event InvoicePaid
tsir make:listener OnInvoicePaid
tsir make:command Ping             # a command `ract` runs (§ 2.6)
tsir make:link-client billing --protocol rest
```

Generator rules (from the brief, made testable):

1. Output compiles under the strictest config with **zero** suppressions.
2. No placeholder that silently passes tests: generated tests **fail** until the body is implemented (`throw new Error('HTP_NOT_IMPLEMENTED')` in the handler, with a failing assertion in the test).
3. No facades, no hidden imports of internals, no `any`.
4. Files are written atomically; existing files are never overwritten without `--force`.
5. Every generator prints the next command to run.

### 2.5 Exit codes and output

| Code | Meaning                                                            |
| ---- | ------------------------------------------------------------------ |
| `0`  | Success                                                            |
| `1`  | Runtime/operation failure (migration failed, deploy invalid)       |
| `2`  | Usage error (bad flag, unknown command)                            |
| `3`  | Environment problem (missing dependency, port taken, no `tsir.js`) |

Output rules: human-readable by default, `--json` for machine use (stable schema, versioned), colour only on TTY, secrets redacted always.

### 2.6 `ract` — the project's own command

Every project gets a `ract` file at its root, the way every Laravel project gets `artisan`:

```
#!/usr/bin/env bun
import { runCli } from '@tsir/console';

process.exitCode = await runCli(process.argv.slice(2));
```

**Decision: no `.js`, no `.ts`, no shim.** An extensionless executable is what the question asked
for, and it was verified rather than assumed (Bun 1.x, 2026-10-29, in this repository):

| Invocation                 | Works | Notes                                                                        |
| -------------------------- | ----- | ---------------------------------------------------------------------------- |
| `./ract route:list`        | ✅    | `#!/usr/bin/env bun`, mode `0755`                                            |
| `bun ract route:list`      | ✅    | the shebang is not needed, so Windows loses nothing                          |
| `bun run ract route:list`  | ✅    | the form a generated `package.json` script uses                              |
| Type annotations inside it | ✅    | Bun's loader accepts TS in an extensionless file                             |
| `node ract`                | ❌    | `ERR_UNKNOWN_FILE_EXTENSION`: Node cannot load `.ts`, and `ract` is Bun-only |

So a `.js` wrapper would be a second file that exists only to satisfy a loader nothing here uses.

**But the generated file carries no type annotations**, even though Bun accepts them, because
three readers meet an extensionless file badly:

- **`tsc --noEmit` does not see it** — with no extension it is not part of the program, so nothing
  in `ract` is type-checked and nothing that wants a type belongs in it.
- **ESLint and Prettier key on the extension**, so both must ignore it _by name_
  (`ignores: ['ract']`, `.prettierignore`). A file they cannot parse should stay trivial.
- **`node --check` and every editor's JS mode** are the fallback readers, and both must succeed.

The rule that follows: **`ract` is a shim, not a program.** If it needs a branch, a type or a
try/catch, the code belongs in `@tsir/console`, where it is tested.

**Windows.** A shebang is inert there, so `bun ract` is the documented form and the generated
`package.json` carries `"scripts": { "ract": "bun ./ract" }`, which is the same command everywhere.
The generated `Makefile` calls `$(BUN) ract`, never a global `tsir`, so a machine with no global
install can still run every project task.

**Why a file in the project and not another global bin.** `php artisan` exists because the command
that runs _is the project's_: it boots the project's config, loads its environment and discovers
its own commands. A global binary would have to be told which project it is in and would still not
be able to see that project's `src/console/commands/`. `ract` is committed, so a reviewer sees
what the project exposes — and it is three lines, so "editable" costs nothing.

**Where the commands come from.** Two sources, and only one of them is configuration:

| Source                         | Kind                               | Why it is not the other way round                                                                               |
| ------------------------------ | ---------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `@tsir/console`'s `COMMANDS`   | the framework's own commands       | one array, shared with `tsir`: two tables would drift the day the second was added                              |
| `tsir.js` → `console.commands` | an **allow-list** of the above     | a deployment that exposes `vault:rotate` on a box that should not have it is a config change, not a code change |
| the app entry's `commands`     | the project's own, `defineCommand` | behaviour lives in exports, exactly like `jobs`, `tasks`, `events`; config only wires                           |

`console.commands` is already declared in the schema and in the `tsir.js` example and is **not
read by anything yet**; `CLI-020` makes it real. The project's own commands are the Laravel
`app/Console/Commands` analogue, and `tsir make:command Ping` scaffolds one.

**What `ract` is not.** It is not a second CLI with a second behaviour: `ract route:list` and
`tsir route:list` run the same function. A project without a `ract` still works — `tsir` remains
the fallback — which keeps the file a convenience rather than a dependency.

## 3. Repository development workflow

```bash
make install          # bun install
make dev              # serve frontpage (Phase 0) / API + frontpage (Phase 2+)
make check            # must be green before pushing
make test
make kill             # stop everything
```

Conventions:

- Commits: Conventional Commits (`feat(http): add timeout middleware`).
- Branches: `feat/<task-id>-slug`, `fix/<task-id>-slug`.
- PR template asks for: task ID, plan diff (if any), failure modes added, security notes.
- No merge without `make check` green and one review (two for `src/framework/vault`, `src/framework/auth`, `src/framework/policy`).

## 4. Failure modes

| Situation                           | Behavior                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------- |
| Port busy, owned by recorded PID    | `make kill` stops it, prints `stopped dev server (pid 1234)`              |
| Port busy, owned by unknown process | Refuses to start; prints `lsof`-style owner and instructions; never kills |
| Record file corrupt                 | Treated as empty, warns, scans only its own known ports                   |
| `bun` missing                       | `make` exits with install instructions                                    |
| CLI run outside a Tsir project      | Exit `3`, "no tsir.js found; run `tsir bootstrap`"                        |
| Generator target exists             | Refuses without `--force`, prints the path                                |
| `--json` output on failure          | Emits `{ ok: false, code, message }` and sets exit code                   |
| Watch mode crash                    | Prints stack, keeps watching, does not clear terminal history             |

## 5. Security considerations

- CLI never prints resolved secret values; `--json` redacts `.secret()` fields the same way logs do.
- `make clean` refuses to delete anything outside the repo root (path prefix assertion).
- `kill-dev.sh` validates every PID against the record file **and** the process start time to avoid PID reuse killing an unrelated process.
- Generators do not fetch templates from the network; templates are versioned with the CLI.
- `tsir new` never writes secrets; it writes `.env.example` and instructs the user to generate keys with `vault:key:generate`.

## Application-first distribution journey (2026-11-01)

`tsir` is the user-facing entry point; the repository Makefile is contributor tooling, not an
application prerequisite. Before publication, the release archive contains a local distribution
with a launcher and installable sibling packages. A user installs its dependencies, adds its
`bin` to `PATH`, runs `tsir new`, installs the generated app's workspace dependencies, and uses `tsir dev`,
`tsir route:list`, and the generators in that app. The launcher chooses an installed project's
own CLI to keep registries and framework versions consistent. `tsir dev` serves an exported HTTP
handler and shuts down cleanly; a lifecycle-only app is still supported. An isolated release
verification must run this workflow, including a real HTTP request and a generated controller,
without importing the source checkout. Package publication, fully automatic cloud provisioning,
and Windows launcher verification remain separate work. Documentation follows the installation →
first application → topic guides → package reference flow, and does not assume Make is installed
by an application developer.

## Distribution layout correction (2026-11-01)

`make dist` must produce a navigable, runnable directory, not just package internals. The root
`tsir` and `bin/tsir` launchers run immediately after the build; `src/apps/http` ships the
actual users and media modules, `src/apps/minimal` demonstrates lifecycle-only boot, and
`src/apps/frontpage` and `src/docs` ship the static sites. `framework/` remains the distributable
package tree, not a substitute for application modules. A release archive excludes dependencies
and must be installed after extraction. `verify-dist` checks the root command and real modular
example; release verification extracts the archive outside the checkout. `dist/` is destroyed on
rebuild, so application projects must be created elsewhere.

### Gap: dist used `apps/` but `tsir make:*` writes under `src/` (fixed 2026-11-01)

`tsir make:module`, `tsir make:controller`, `tsir make:model`, and the other `make:*` generators
write application files under `src/modules/<module>/…`. A generated application's source root is
`src/`. The distribution mirrored the monorepo's `src/apps/` as a top-level `apps/` directory,
which was inconsistent with the layout a consumer sees and which the generators target. A reader
following `installation.md` or `dist/README.md` found `apps/examples/http/src/modules/…` while
`tsir make:module` created `src/modules/…` — two different names for the same concept.

**Fix:** rename the distribution's top-level `apps/` to `src/`. The monorepo source tree keeps
`src/apps/` (it is the repo's organisation, not a consumer-facing path); only the generated
`dist/` tree changes. After the rename:

```text
dist/
├── src/
│   ├── examples/http/src/modules/{users,media}/
│   ├── examples/minimal/
│   ├── frontpage/
│   └── docs/
├── framework/<pkg>/
└── frontpage/                 # compatibility copy
```

## Module-owned controller generation (2026-11-01)

`tsir make:module shop` creates the module explicitly. `tsir make:controller order shop` and
`tsir make:model order shop` place kebab-case files in `src/modules/shop/`; neither creates a
missing module. The controller uses the module registry, inherits its deploy unit unless `--unit`
is explicit, and is not auto-imported. The model is a Drizzle schema, not a database or migration.
Documentation shows registration, route verification and replacement of intentionally failing tests.
Archive-only verification exercises these commands, route compilation, HTTP and schema loading.

## Module-local migrations and seeders (2026-11-01)

Seeders live with their module and are explicitly registered in the app's seeders array.
A module migration has its own Drizzle journal, snapshots and SQL under the module; operators select
it explicitly with `tsir migrate shop`. Per-module/connection database bookkeeping is isolated and
PostgreSQL runs share a connection-level lock. Existing project-wide journals remain supported.
No cross-module execution order is inferred; document dependencies, schema scope, dialects,
rollback and verification against throwaway databases. External release checks generate real
SQLite and PostgreSQL migrations; SQLite-backed tests verify journal isolation.

## Dist-root CLI experience (2026-11-02)

Running `make dist` and then invoking `./tsir` from the `dist/` root produced four
broken or misleading experiences that made the distribution feel unusable for
testing modules:

| Command from `dist/` root | Before                                                             | Problem                                                                               |
| ------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `./tsir dev`              | `✗ no tsir.js found` ↳ `run tsir bootstrap …`                      | Circular: `bootstrap` also requires `tsir.js`. No pointer to the bundled examples.    |
| `./tsir bootstrap`        | asks topology → `✗ no tsir.js found`                               | Wastes the user's keystroke; fails only after prompting.                              |
| `./tsir new wew`          | `create applications outside the generated distribution directory` | Correct refusal, but no actionable command — the user is stuck inside the dist.       |
| `./tsir make:module shop` | `✓ created src/modules/shop/…`                                     | Silent success writing into the distribution's own `src/`, wiped on the next rebuild. |
| `./tsir doctor`           | `✗ project` ↳ `run tsir bootstrap …`                               | Generic hint, not dist-aware.                                                         |

**Root cause.** `dist/` is a Bun workspace of framework packages and example
apps, not an application. Every project-bound command calls `findConfigFile()`,
which walks up from `cwd` looking for `tsir.js` and throws when none is found.
The throw carried a hint that assumed the caller was in an app directory, not
inside a distribution.

**Fixes applied:**

1. **`findDistRoot()`** (`src/framework/console/src/project.ts`): walks up from
   `startDir` and returns the directory that contains both `manifest.json` and
   `framework/console/package.json` — the two files `make dist` emits that a
   plain app does not. Returns `undefined` outside a distribution.
2. **`findConfigFile()` hint is now dist-aware.** When `findDistRoot` finds a
   dist, the "no tsir.js found" hint points at the bundled examples for testing
   (`tsir dev --app src/apps/http`) and tells the user to `cd` out of the
   distribution before `tsir new`. Outside a dist the original hint
   (`tsir bootstrap` / `tsir new`) is preserved.
3. **Global `--app <path>` flag** (`src/framework/console/src/index.ts`): any
   project-bound command can run from outside its directory by passing
   `--app <path>` (or `-C <path>`, matching `make -C` / `git -C`). Implemented
   by `process.chdir(path)` before dispatch, so all 31 `loadProject(process.cwd())`
   call sites pick up the right root with no per-command changes. The hint from
   fix #2 now recommends `tsir dev --app src/apps/http` instead of `cd`.
4. **`bootstrap` fails fast.** `findConfigFile(cwd)` runs before the TTY check
   and the topology prompt, so a missing project is reported before any question
   is asked.
5. **`tsir new` guard names the next command.** The refusal hint now prints the
   absolute launcher path: `cd to another directory and run <dist>/tsir new <name>`.
6. **`make:module` warns without a project.** It still writes the files (a user
   may be scaffolding a directory before adding `tsir.js`), but emits
   `! no tsir.js found … the module is written but not registered by any app`
   so the output is not mistaken for a working module.
7. **`doctor` surfaces the error's own hint.** The project check now uses the
   `CliError.hint` from `loadProject`'s failure (dist-aware) instead of a
   hardcoded generic hint.

**Verification.** `bun test src/framework/console` (565 pass) and
`bun run verify-dist` both pass. Manual checks from `dist/`:

```bash
./tsir dev                       → dist-aware hint recommending --app src/apps/http
./tsir dev --app src/apps/http → boots the http example from the dist root
./tsir route:list --app src/apps/http → lists 6 routes
./tsir make:module shop --app src/apps/http → writes into http example's src/modules/
./tsir bootstrap                 → fails immediately with the same hint
./tsir new wew                   → refusal with the exact command to run outside the dist
./tsir make:module               → warning, then writes (correct for a project-less dir)
./tsir doctor                    → project check carries the dist-aware hint
```

## Module layout restructure (2026-11-02)

Modules no longer live under `src/modules/`. Each module is a **direct child of the app root**
and owns its components in typed subdirectories:

```text
<app>/
├── tsir.js
├── app.ts
├── config.ts
├── routes.gen.ts
├── orders/                     ← a module
│   ├── index.ts                ← public surface (only thing other modules import)
│   ├── routes.ts
│   ├── http/orders.controller.ts
│   ├── models/order.model.ts
│   ├── services/order.service.ts
│   ├── queues/send-receipt.job.ts
│   ├── events/order-placed.event.ts
│   ├── listeners/notify-warehouse.listener.ts
│   ├── middleware/
│   ├── guards/
│   ├── policies/
│   ├── seeders/
│   ├── migrations/
│   └── console/
├── shared/                     ← cross-module code that has no owner
└── console/                    ← app-level commands (tsir make:command)
```

**What changed:**

- Modules are at the app root, not nested under `src/modules/`. `tsir.js`, `app.ts`, and
  `config.ts` are also at the app root — there is no `src/` wrapper around application code.
- `make:*` generators accept an `app/module` argument: `tsir make:controller order shop`
  creates `shop/http/order.controller.ts`. With no app prefix, the current working directory
  is the app root.
- `make:command` stays app-level in `console/` (commands are not module-owned).
- `dist/` ships apps under `dist/apps/` (not `dist/src/apps/`). `dist/` is wiped on every
  `make dist`, so the shipped example apps are always in sync with `src/apps/`.
- `check-modules.ts` discovers modules by scanning each app root for directories that export
  an `index.ts`; it no longer looks for a `src/modules/` marker.
- Controller globbing (`**/*.controller.ts`) already finds files in `<module>/http/`, so the
  route compiler needs no change.

**Two new example apps ship with the dist:**

| App                        | Demonstrates                                            |
| -------------------------- | ------------------------------------------------------- |
| `todo-app-example.com`     | Svelte 5 drag-and-drop todo, UUID IDs, static frontend  |
| `full-actions-example.com` | HTTP + SQS-style queues + events + listeners end-to-end |

**Verification:** `bun test src/framework/console` (565 pass), `bun run dist`,
`bun run verify-dist`, and `bun src/tools/check-modules.ts` all pass; every example app's own
test suite is green.
