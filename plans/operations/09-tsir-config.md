# 09 — `tsir.js`: Canonical Project Configuration

> One file describes the application: modules, http, console, deploy. Presets make it one-liner for the common case; managed regions make automation safe. **No secrets in `tsir.js`.**

---

## 1. What `tsir.js` is

`tsir.js` is the **canonical project configuration file** for a Tsir application, analogous to `vite.config.ts` or `nuxt.config.ts` in shape but backend-only in scope. It:

1. Declares **which capabilities** the app uses (`modules`).
2. Declares **how they are wired** (`http`, `console`, `database`, `queue`, …) with typed options.
3. Declares **where it deploys** (`deploy.targets`, `deploy.topology`).
4. Carries **build-time metadata** (route roots, generator output paths, OpenAPI output).

It does **not** carry secrets, environment-specific connection strings, or anything that must differ between staging and production without a redeploy of config. Those come from validated environment variables (`03-core.md § 4`).

### 1.1 File resolution

Searched in order, first match wins:

1. `tsir.config.js` (explicit alias, for teams that prefer a namespaced name)
2. `tsir.js`
3. `tsir.mjs` (when the project is `"type": "commonjs"`)

`tsir.js` is the canonical name used in docs, generators, and error messages. If more than one candidate exists in the same directory, startup fails (`CFG_AMBIGUOUS_CONFIG_FILE`) instead of guessing.

### 1.2 Format rules

- Must be an ES module exporting `defineConfig(...)` (a plain object default export is also accepted and normalized).
- May be TypeScript-in-JS (type annotations are **not** allowed at runtime — Bun can load `.ts`, but the canonical file stays `.js` for portability; `tsir.config.ts` is accepted via the same loader when `bunfig` allows it).
- Must be **synchronous** at module scope. Async config is a design smell: anything dynamic belongs in env vars or a preset resolving at `tsir` startup.
- Is loaded once, at `tsir` command start or app bootstrap; the resolved object is frozen and passes through the config schema validator.

## 2. Shape

```js
// tsir.js — generated by `tsir new`, owned by the project
import { defineConfig, preset } from '@tsir/config';

export default defineConfig({
  preset: preset.standard(), // batteries: http + console + database + vault

  app: {
    name: 'acme-api',
    env: { fromEnv: 'APP_ENV', default: 'development' },
  },

  paths: {
    src: 'src',
    controllers: ['src/features/**/*.controller.ts'],
    routes: 'src/routes.gen.ts',
    migrations: 'drizzle',
  },

  modules: [
    '@tsir/http',
    '@tsir/database',
    '@tsir/vault',
    '@tsir/console',
    // '@tsir/queue',   ← opt-in, commented by the generator
    // '@tsir/auth',
  ],

  http: {
    port: { fromEnv: 'HTTP_PORT', default: 3000 },
    globalMiddleware: ['requestId', 'logging', 'cors'],
    defaultTimeoutMs: 30_000,
    maxBodyBytes: 1_048_576,
    trailingSlash: 'strict',
    openapi: { enabled: true, path: '/__tsir/openapi.json', title: 'Acme API' },
  },

  // Named connections (ADR-0019): `default` names the one every unnamed
  // call site uses; each entry is an independent connection with its own
  // driver, pool and capabilities. One entry is the single-connection case.
  database: {
    default: 'app',
    connections: {
      app: {
        driver: 'd1', // ADR-0016. The union is 'd1' | 'postgres' | 'mysql' (ADR-0020)
        binding: 'DB', // D1 names the deploy binding; postgres and mysql use `url`
        logging: 'slow',
        slowQueryMs: 200,
      },
      // reporting: {
      //   driver: 'postgres',
      //   url: { fromEnv: 'REPORTING_URL', secret: true },
      //   pool: { max: 4 },
      //   required: false,
      // },
      // legacy: {
      //   driver: 'mysql', // MariaDB included: same driver (ADR-0020)
      //   url: { fromEnv: 'LEGACY_DATABASE_URL', secret: true },
      //   pool: { max: 4 },
      //   required: false,
      // },
    },
  },

  // Phase 7 — declared here so the shape is decided once (`15-capabilities.md` § 2.2).
  // cache: {
  //   default: 'app',
  //   stores: {
  //     app:      { driver: 'database' },
  //     sessions: { driver: 'database', table: 'sessions', required: true },
  //     local:    { driver: 'memory' },
  //   },
  // },
  // queue: {
  //   default: 'default',
  //   connections: {
  //     default: { driver: 'cloudflare-queues' },
  //     heavy:   { driver: 'sqs', queueUrl: { fromEnv: 'HEAVY_QUEUE_URL' } },
  //     sync:    { driver: 'sync' },
  //   },
  // },

  vault: {
    // ── managed region: managed:vault:start ──
    keys: {
      now: { fromEnv: 'APP_KEY_NOW', secret: true },
      next: { fromEnv: 'APP_KEY_NEXT', secret: true },
    },
    // ── managed region: managed:vault:end ──
  },

  // The commands `ract` exposes, by name (`11-dx.md § 2.6`). An allow-list of the framework's
  // own commands — the project's *own* commands are an export of the app entry, not config.
  console: {
    commands: ['migrate', 'migrate:status', 'db:seed', 'vault:rotate'],
  },

  deploy: {
    topology: 'separate',
    targets: {
      cloudflare: { entry: 'units' },
      lambda: { region: 'ap-southeast-1', architecture: 'arm64', memoryMb: 1024 },
      bun: {},
    },
    units: {
      // default graph is derived; overrides only where necessary
      admin: { enabled: true, target: 'cloudflare' },
    },
  },

  presets: [], // additional named presets, applied left→right
  strict: true, // unknown keys are errors, not warnings
});
```

### 2.1 Environment references

Any leaf value may be `{ fromEnv: 'NAME', default?: T, secret?: boolean }`. The loader resolves it against the process environment **at bootstrap**, validates the type, and reports missing/secret values in the config report. This is the only sanctioned way for `tsir.js` to reference dynamic values — no `process.env.X` reads inside `tsir.js`.

Precedence remains: **env → tsir.js resolved value → schema default** (`03-core.md § 4.1`).

### 2.2 Named registries (ADR-0019)

Every driver-based block has the same two-level shape: **`default` names an entry, and a map holds the
entries.** That is true for `database.connections`, and (Phase 7) `cache.stores`, `queue.connections`,
`mail.mailers`, `storage.disks`.

```js
database: { default: 'app', connections: { app: { … }, reporting: { … } } },
```

- **The key is a purpose, never a driver.** `app`, `reporting`, `cache`, `heavy` — a project may hold
  three connections with the same driver, and the name is what distinguishes them.
- **`default` is required and must exist.** A `default` naming a missing entry is
  `CFG_UNKNOWN_DEFAULT`; a missing `default` is `CFG_MISSING_DEFAULT`. There is no "first key wins".
- **Names become a type.** `tsir build` emits the connection/store names as a literal union, so
  `db.connection('reportng')` is a compile error in application code and a `DB_UNKNOWN_CONNECTION`
  at runtime — the second is for a `tsir.js` edited without a rebuild.
- **One entry is the single-connection case.** The generator writes `default` + one entry; it never
  emits a flat `{ driver }` block, so the shape does not change on the day a second connection
  appears.
- **`tsir make:connection --port=database --name=reporting`** scaffolds one entry, adds the entry to
  the manifest the deploy adapter reads, and (for D1) refuses to invent a binding that
  `wrangler.toml` does not declare.
- **`tsir bootstrap --migrate-config` upgrades the old flat block** (`database: { driver, url }`) to
  `default: 'app', connections: { app: { … } }` with the same values, as a real config-format migration
  (§ 5.3), not a silent rewrite at boot.

## 3. Presets

A preset is a function returning a partial config; presets are composed left→right with later winning (deep-merged for objects, replaced for arrays unless the array is declared `merge: 'append'`).

| Preset                | Includes                                                          | Use case                    |
| --------------------- | ----------------------------------------------------------------- | --------------------------- |
| `preset.minimal()`    | `core` only                                                       | Library-ish services, tests |
| `preset.standard()`   | http, console, database, vault, validate                          | Default API service         |
| `preset.api()`        | standard + auth, policy                                           | Public API with RBAC        |
| `preset.worker()`     | http, queue, events, schedule, pulse                              | Background processing       |
| `preset.edge()`       | http, link/rest, pulse, cloudflare target, `topology: 'separate'` | Edge-first service          |
| `preset.serverless()` | http, link/rest, lambda target                                    | Classic Lambda API          |
| `preset.full()`       | everything available                                              | Examples and evaluation     |

Rules:

- Presets only **add** defaults; they never remove explicitly configured values.
- A preset that references a module not installed is a boot error (`CFG_PRESET_MODULE_MISSING`) with the `bun add` command.
- Third-party presets are allowed (`preset from 'acme-tsir-preset'`) but must export a version and are recorded in the resolved config dump.

## 4. Managed regions (automation)

The file is **governed**: `tsir` may rewrite marked regions without touching the rest.

```js
// ── managed:routes:start ─────────────────────────────
// routes: compiled output lives in src/routes.gen.ts
// ── managed:routes:end ───────────────────────────────
```

Rules:

1. Managed regions are delimited by `// ── managed:<id>:start` / `:end`. Nested regions are invalid.
2. `tsir doctor --fix` reports unmanaged drift, never rewrites unmanaged text.
3. Writes are atomic (temp file + rename), preserve formatting outside the region, and are idempotent.
4. If a managed region is malformed or missing, `tsir` **fails loudly** (`CFG_MANAGED_REGION_INVALID`) instead of re-generating and clobbering user code.
5. Every automated write is printed: `✓ updated tsir.js (managed:vault, managed:deploy)`.

This is what makes "automated configuration / bootstrap for all" safe: the tool can maintain its own sections without becoming a code generator that owns your file.

## 5. Bootstrap automation (`tsir bootstrap`)

The "bootstrap for all" capability the brief asks for, expressed as explicit, reviewable steps:

```bash
tsir bootstrap                 # detect, plan, apply
tsir bootstrap --plan          # print the plan as a diff, change nothing
tsir bootstrap --set preset=api --set deploy.topology=single --set modules+=@tsir/queue
tsir bootstrap --interactive   # prompts (default when TTY and no flags)
```

### 5.1 Detection

| Signal                                       | Inferred                                                    |
| -------------------------------------------- | ----------------------------------------------------------- |
| `package.json` deps                          | installed `@tsir/*` modules                                 |
| Presence of `drizzle.config.ts` + `drizzle/` | database + migrations enabled                               |
| `wrangler.toml`                              | Cloudflare target enabled                                   |
| `template.yaml` / `cdk.json`                 | Lambda target enabled                                       |
| `Dockerfile` / `fly.toml`                    | Bun target                                                  |
| `.env.example` keys                          | suggested schema entries (reported, never applied silently) |
| Existing `tsir.js` version marker            | which migrations of the config format to run                |

### 5.2 Plan → apply

1. Compute the desired config: preset + modules + targets + managed regions.
2. Validate against the config schema. **A plan that does not validate is never applied.**
3. Print a unified diff. In non-interactive mode, apply only with `--yes`.
4. Apply: rewrite managed regions, add missing keys, never delete keys the user wrote (report them as `unused` instead).
5. Write `.tsir/manifest.json`: config format version, applied presets, generated-file hashes.
6. Print next steps (`bun add …`, `tsir make:controller …`, `tsir deploy:plan`).

### 5.3 As built (2026-10-28)

`tsir bootstrap` exists and does the deploy half of § 5:

| Flag                          | Behaviour                                                                     |
| ----------------------------- | ----------------------------------------------------------------------------- |
| `--plan`                      | detect, render `managed:deploy`, print the `-`/`+` diff, write nothing        |
| `--yes`                       | apply, atomically (temp file + rename); without it nothing is written         |
| `--target a,b`                | override detection for this run                                               |
| `--topology separate\|single` | the topology written into the region (default `separate`, written explicitly) |
| `--json`                      | the same plan, machine-readable                                               |

Detection reads files, not intentions: `wrangler.toml`/`wrangler.jsonc` → Cloudflare,
`template.yaml`/`template.yml`/`cdk.json` → Lambda, `Dockerfile`/`fly.toml` → Bun. With no
signal it declares the Bun target and says so, because a project with no cloud marker still
deploys somewhere.

The managed-region writer lives in `@tsir/config` (`managedRegions`, `applyManagedRegion`,
`renderRegion`, `diffLines`) and enforces § 4's rules: unclosed, stray, mismatched, nested
and duplicated fences all raise `CFG_MANAGED_REGION_INVALID`; writes are idempotent, keep the
region's own fences byte-for-byte, and touch nothing outside them.

Still open in this section: presets (`CFG-102`/`CFG-103`), `.tsir/manifest.json` as the
config-format record (`CFG-105` — the file currently belongs to `tsir build` and holds the
production manifest, so bootstrap deliberately does not write it), config-format migrations
(`CFG-106`), `--set` (`CFG-110`), interactive prompts (`CFG-111`), unmanaged-key reporting
(`CFG-112`), and the secret-in-file detector (`CFG-114`).

### 5.4 Config format migrations

`.tsir/manifest.json` records `configVersion`. When `tsir` starts and finds a newer format, it refuses to run and prints `tsir bootstrap --migrate-config`, which applies deterministic, snapshot-tested transforms from one version to the next.

## 6. Validation rules

| Rule                                                                         | Behavior                                                    |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Unknown top-level or nested key with `strict: true`                          | Boot error, suggests nearest valid key (edit distance)      |
| Module declared but not installed                                            | Boot error with install command                             |
| Module installed but not declared                                            | Warning at `tsir doctor` (not boot)                         |
| Secret-looking value inlined (e.g. 64-char base64 under `database.url`)      | **Error**: "put this in env, not tsir.js"                   |
| `deploy.targets` empty while modules require deployment                      | Warning                                                     |
| `http.port` unresolved and not in dev                                        | Boot error                                                  |
| Managed region malformed                                                     | Boot error                                                  |
| Registry without `default`, or `default` naming a missing entry              | `CFG_MISSING_DEFAULT` / `CFG_UNKNOWN_DEFAULT`               |
| Registry entry with both a `binding` and a `url`                             | `CFG_AMBIGUOUS_CONNECTION` (a connection has one transport) |
| `*.default` names a `memory`/`sync`/`null` entry while `NODE_ENV=production` | Boot error, names the entry and the portable alternative    |
| Config file has syntax error                                                 | Boot error with source location                             |

## 7. Failure modes

| Code                         | Cause                                        | Remediation printed                               |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------- |
| `CFG_CONFIG_NOT_FOUND`       | No `tsir.js`                                 | "run `tsir bootstrap` or `tsir new`"              |
| `CFG_AMBIGUOUS_CONFIG_FILE`  | Two candidates                               | Lists both, asks to keep one                      |
| `CFG_CONFIG_INVALID`         | Schema failure                               | All issues at once, with paths                    |
| `CFG_MODULE_NOT_INSTALLED`   | `modules` entry missing from `node_modules`  | `bun add @tsir/queue`                             |
| `CFG_SECRET_INLINED`         | Secret literal in file                       | "move to env var"                                 |
| `CFG_PRESET_MODULE_MISSING`  | Preset requires absent module                | Exact install list                                |
| `CFG_MANAGED_REGION_INVALID` | Malformed markers                            | Shows line numbers                                |
| `CFG_CONFIG_VERSION_STALE`   | Old format                                   | `tsir bootstrap --migrate-config`                 |
| `CFG_BOOTSTRAP_INVALID_PLAN` | Plan fails validation                        | Prints the failing diff hunk                      |
| `CFG_MISSING_DEFAULT`        | Registry has no `default`                    | Shows the exact key to add                        |
| `CFG_UNKNOWN_DEFAULT`        | `default` names an entry that does not exist | Lists declared names                              |
| `CFG_AMBIGUOUS_CONNECTION`   | Entry has both `binding` and `url`           | "keep one: D1 uses bindings, Postgres uses a URL" |

## 8. Security considerations

- **No secrets in `tsir.js`.** The validator actively rejects high-entropy literals in secret-typed positions and prints remediation. Enforced lint + boot check, because this is the single most likely accidental secret leak in a config file.
- `tsir.js` is committed; `.env` files are gitignored by the generator's `.gitignore` additions.
- `tsir bootstrap --plan` output redacts any resolved env values it would print.
- Presets from third parties execute at config load (they are code). The docs state this plainly; `bootstrap` never installs a preset without explicit user action.
