## Gate notes

- CFG-117: `nextSteps` is pure and ordered (plan → build → validate → ract); 4 tests in `bootstrap-next-steps.test.ts`.
- DXS-011: withdrawn — see the row. `tsir deploy:plan`, `deploy:diff`, `deploy:build`, `deploy:validate` and `openapi:generate` exit 0 with no cloud credentials; `openapi:generate` produces 6 operations on the HTTP example, matching `route:list`.
- DXS-015: `make make-check` runs `src/tools/check-make.ts` (part of `make check`). Reading a document as a transcript is deliberately narrow: only a code span, a fenced block, or a line that starts with the command counts, because "no test can make it so" is English and a gate that cries wolf gets switched off. 16 tests in `check-make.test.ts`.
- DXS-012: `make check` runs `boundaries` and `docs-pr` (`src/tools/check-docs-in-pr.ts`). The git path is tested in throwaway repositories. In this workspace, which is not a git repository, the gate skips with a note.
- DXS-009: `make db-up`/`db-down` run Compose against `compose.yaml`. Verified with Docker: Postgres 16 on 127.0.0.1:5432, and the database-backed suite passes 30 of 30 against it.
- CFG-102: seven built-in presets, applied before the zod parse in `loadProject`. `presets-boot.test.ts` boots a fixture project per preset to `ready`, with the framework packages linked the way `bun install` links them (8 tests).
- CFG-103: order-sensitive merge tested: scalars later-wins, objects deep-merge, arrays replace unless `appendList`, inputs never mutated.
- CFG-109: detection reads the marker files, then `package.json` dependencies, then `.env.example` (Cloudflare variables only). Seven tests cover the signals, a malformed `package.json`, comments in `.env.example`, and the AWS-variable exclusion.
- CFG-113: `CFG_PRESET_MODULE_MISSING` names every missing preset module; the top-level `modules` key is checked too (`CFG_MODULE_NOT_INSTALLED`), each with the exact `bun add` line.
- CFG-105: `bootstrap --yes` writes `.tsir/bootstrap.json` (decision: not `manifest.json`, which `tsir build` owns). It holds the config format, a sha256 of the deploy block, the targets and topology, and the applied presets. It is deterministic, so a second run leaves the same bytes. `tsir start` warns on drift: changed presets, a newer config format, or a corrupt file. Tests: 14 in `bootstrap-record.test.ts`.
- CFG-118: a third-party preset is `definePreset({ name, version, layer })` and is refused without a name or version. The applied presets, with name, version and source, are written to `.tsir/bootstrap.json` on apply, and `tsir start` warns if they change.
- CFG-122: the database presets (`standard`, `api`, `full`) set `database.default` to `primary`, and never name a driver. The project declares `primary` and its driver. A missing `primary` is refused at load (`CFG_UNKNOWN_DEFAULT`). Code switches connections with `db.connection(name)` (DB-019), as Laravel's `DB::connection()` does.
- CFG-110 and CFG-111: `--set` (`deploy.topology`, `deploy.targets`, `modules+=`) and the prompts are in `bootstrap.ts`. A terminal is asked for topology and then for approval; a non-TTY run without `--yes` or `--plan` aborts with a usage error. `bootstrap()` takes an injectable `io`, so tests run without a TTY (39 bootstrap tests pass).
- CFG-112 to CFG-119: leftovers are reported and never deleted; one secret detector guards both the load and bootstrap; `config:dump --json` carries the schema; `doctor --fix` writes only the managed region; `docs-pr` runs under `make check`.
- Decision: `tools/check-plans.ts` reading `plans/` stays as it is (the owner accepted it).
- CLI ships its first real commands (`dev`, `doctor`, `route:list`, `migrate`) in Phases 1–3; generators follow the modules they generate.
- A generator may not ship before the module it targets has a stable public API.

### Application-first distribution journey (2026-11-01)

- `tsir`, not repository Make targets, is the supported application CLI. The pre-publication
  archive supplies a launcher and local package dependencies; generated apps use the matching
  distribution as a Bun workspace. Relocating or deleting it requires updating the generated
  workspace path; registry publication remains open.
- Verify outside the checkout: install distribution, scaffold, install the app, serve an HTTP
  request, generate/register a controller, list routes, run tests, and build a manifest. Platform
  releases and real cloud deployments remain separately verified work.

### Distribution layout correction (2026-11-01)

- The repository build must leave an immediately runnable root `tsir` and `bin/tsir`, a README,
  application examples with their real modules, static apps, and the framework package tree.
- Release verification must extract the archive outside the checkout and exercise both the
  distributed modular HTTP example and a newly generated modular app; installed dependencies must
  not be shipped in the archive. Never treat a generated build directory as a user's project home.

### Module-owned controller generation (2026-11-01)

- `make:controller` requires an explicitly named existing module and does not overwrite its
  registry or public index. The app imports the controller and registers the module; generated tests
  remain intentionally red.
- Verify the CLI, docs and release artifact outside the checkout, including a controller added to
  an existing module, route compilation and HTTP requests. Update the distribution and application
  trees in installation documentation rather than assuming a repository layout.

### Explicit module arguments (2026-11-01)

Controller, model, service, middleware, guard, job, event, listener, seeder and link-client
generators support `tsir make:<kind> <name> <module>`, for example
`tsir make:module shop`, `tsir make:controller order shop`, and `tsir make:model order shop`.
Kebab-case resources such as `user-settings` map deterministically to files within the named
module and PascalCase TypeScript symbols. Controller and model generation require an existing
module and never infer or silently create one. Models are explicit Drizzle schemas, not Active
Record; SQLite is the default, with an opt-in PostgreSQL dialect. Verify the exact commands in an
isolated distribution, including module ownership, routes, and model schema loading.

### Module-local migrations and seeders (2026-11-01)

- `make:seeder order shop` writes a seeder within an existing module; explain explicit registration.
- `make:migration create-orders shop` generates a module-local Drizzle journal and snapshots under
  `src/modules/shop/migrations/`. Support explicitly selected module journals in migrate, status,
  verify and rollback, with separate database bookkeeping per module and connection while sharing
  the connection-level migration lock. Preserve the existing project-wide path and commands.
- Document explicit schema, dialect, connection selection, cross-module ordering limitations and
  the fact that generation does not apply migrations. Verify isolated journals, safe refusal and
  generation with real Drizzle tooling in the external release journey.
