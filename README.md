## Why Tsir

An early-stage team does not need a platform. It needs a **bill of zero** for as long as
possible, and a codebase that does not have to be rewritten on the day the first customer
arrives. Those two goals usually fight each other: the cheap stack is a pile of glue code,
and the comfortable stack costs money before it earns any.

Tsir is built for the overlap.

- **Runs where it is free.** Cloudflare Workers with D1 is the default target — that is the
  fastest free tier in the business, and the same handler code also builds for Bun and AWS
  Lambda without a rewrite.
- **Nothing to pay for.** MIT licensed, no seat count, no hosted control plane, no
  open-core feature wall. Two runtime dependencies (`zod`, `drizzle-orm`), both widely used
  and both tree-shaken out of what you do not import.
- **No magic to outgrow.** Routes, providers and jobs compile into immutable registries at
  build time; there is no reflection, no service locator, and no global container. What you
  write is what runs — so a 3-person team can read the whole stack.
- **Honest over impressive.** Capabilities are declared and enforced at boot. D1 has no
  interactive transactions, so the framework says so and gives you `batch()` and optimistic
  concurrency instead of a fake transaction. Claims in the docs carry a test or a
  measurement; the badge above is generated by `make readme`, not typed by hand.

## Quick start

Install Bun and the pre-alpha distribution as described in the
[installation guide](./src/docs/installation.md). Then, from a directory outside the distribution:

```bash
tsir new hello
cd hello
bun install --ignore-scripts
tsir dev
```

Open `http://127.0.0.1:3000`. The `tsir` command is the application entry point. Packages are
not published to npm; the installation guide explains the local distribution workspace and its
limitations. Continue with [controllers](./src/docs/guides/controllers.md),
[models and Drizzle](./src/docs/guides/database.md), [queues](./src/docs/guides/queues.md),
[cache](./src/docs/guides/caching.md), [configuration](./src/docs/guides/configuration.md), and
[cloud providers](./src/docs/guides/providers.md).

### Framework contributors

The repository Makefile is for building and testing Tsir itself, not for running application
projects. See [contributor commands](./src/docs/guides/make.md); `make help` lists all targets.

## What is real today

The framework is **pre-alpha**. Phase 7 (capabilities) is closed with caveats, and Phase 8 (production
readiness) is in progress. The database, the capability modules and the CLI are built, tested and gated
in CI, but no capability has yet run on a real Worker or Lambda, and nothing is published to npm yet. That said, the parts that exist are tested and gated in CI:

| Working now                                                                                | Planned                                     |
| ------------------------------------------------------------------------------------------ | ------------------------------------------- |
| DI container, typed config, lifecycle, validation, router, HTTP pipeline, OpenAPI          | Streaming requests, response validation     |
| D1 and Postgres, Drizzle, migrations, seeders, column encryption                           | MySQL driver; real Worker/Lambda deployment |
| Capabilities: cache, queue, events, schedule, storage, mail, notify, policy, auth, pulse   | Admin surface and live cloud verification   |
| `@tsir/link` — REST, gRPC, SOAP, WS + rooms; `tsir` CLI; `dist/` verified for both targets | Publishing to npm                           |

The full, honest inventory — including what is explicitly _not_ built — is the set of package
READMEs under [`src/framework/`](./src/framework); the phase and status the badges claim are the
ones `status.json` records. Every design decision is written down before it is built, and each
one is cited from the code by its `ADR-nnnn` id.

## Contributing

Four rules, enforced in review:

1. **Write it down first.** A change that contradicts a recorded decision amends it in the same
   pull request.
2. **No new runtime dependency without an ADR** — and it must be ESM and tree-shakeable.
3. **No claim without evidence.** A performance or security statement carries a committed
   benchmark or a test, or it is removed.
4. **Every module documents its failure modes**, not just its happy path.

Proposing something new? A feature, a breaking change, or tooling that improves the project
itself goes through [`rfc/`](./rfc/README.md): copy [`0001-sample-template-here.md`](./rfc/0001-sample-template-here.md),
fill it in, and open a pull request. Bugs go to the issue tracker — an RFC is a proposal, never
a bug report.
